КУРСОВАЯ РАБОТА — ПОЛНЫЙ КОМПЛЕКТ
Григорьев Антон Александрович, ПИ-2-25
Тема: Разработка базы данных для администрирования и автоматизации процессов тренажерного зала.

СОСТАВ
• Пояснительная записка: 69 страниц, Word и PDF.
• Презентация: 16 слайдов, PowerPoint и PDF.
• SQL: файлы 00–11.
• Скриншоты: пять реальных снимков pgAdmin 4, включённых в записку.
• Заявление на тему и бланк отзыва: Word и PDF.
• Протоколы проверок и описание опыта с двумя соединениями.

С НУЛЯ
Нужны PostgreSQL 17, расширение btree_gist и pgAdmin 4.
1. Подключиться к своему серверу от postgres / владельца базы.
2. В Query Tool базы postgres выполнить только файл 00_Создать_базу.sql,
   вне BEGIN/COMMIT и с включённым Auto-commit.
3. Обновить список баз и открыть Query Tool именно базы gym_course.
4. Выполнить 01, затем 02, 03 и 04. Файл 05 — необязательный опыт с индексами.
5. Выполнить 06, 07, 08 и 09.
6. Выполнить 10 и 11 для проверки. Они завершаются ROLLBACK.
   Для подробного просмотра Data Output выполнять проверочные блоки по очереди
   в одном Query Tool: временные таблицы доступны только до ROLLBACK.
7. Для дальнейших операций использовать SET TIME ZONE 'Europe/Moscow'.
   Изменения поддерживаются на стандартном READ COMMITTED.

ЕСЛИ УСТАНОВЛЕН ЭТАП 2
Повторно файлы 00–04 не выполнять. Добавить 06, 07 и 09;
файл 08 содержит запросы на чтение. Затем выполнить 10 и 11.
Если часть новых файлов уже выполнена, повторное создание объектов приведёт
к сообщению «already exists»: нужно выполнять только ещё не установленные файлы.
Файлы начальной загрузки и создания объектов рассчитаны на один запуск.

РОЛИ
gym_admin — доверенный владелец объектов;
gym_manager — работа с клиентами и операциями, без DELETE, DDL и аудита;
gym_analyst — чтение трёх аналитических представлений без контактов клиентов.
Это групповые NOLOGIN-роли, не отдельные учётные записи с паролями.
Для проверки от postgres используется SET ROLE / RESET ROLE, как в файле 10.
Реальным пользователям роли назначаются командой GRANT gym_manager TO имя_логина.

ЧТО ПРОВЕРЕНО
• Повторная установка в пустую отдельную базу: файлы 01–10.
• 34 автоматических сценария: 25 для правил и аудита, 9 для прав.
• Два одновременно работающих соединения: переплата и последнее место.
• Отказ записи на неподдерживаемом REPEATABLE READ.
• Полная транзакция менеджера: клиент → продажа → оплата → занятие → запись.
• Итог: 11 таблиц, 28 триггеров, 4 представления, 12 прикладных запросов,
  27 B-tree-индексов и один GiST-индекс.
• В рабочем наборе по 15 строк, bookings — 16, audit_log — 30.
Тесты могут оставлять пропуски в последовательностях — это нормальное поведение.

ГРАНИЦЫ МОДЕЛИ
Операции изменения сериализуются общей advisory-блокировкой; это учебное
решение для небольшого стенда, а не обещание высокой производительности.
Владелец и суперпользователь доверенные: они могут изменить триггеры и журнал.
Возврат, нарушающий полную оплату существующей неотменённой записи, запрещён.
Дата возврата не хранится; финансовая сводка относится к исходной дате оплаты.
Приложение, эквайринг, зарплаты и перерасчёты за посещённые занятия не входят в работу.
